# Admin match-file submissions (T6)

The console file endpoint is `POST /api/admin/uploads/file` (multipart). It accepts only `file`, stable `operationId`/`itemId`, and `programId`. A new match also requires the chosen canonical roster `playerId`, `date` (`YYYY-MM-DD`), `matchType` (`Singles`/`Doubles`), and `courtType` (`Hard`/`Clay`/`Grass`/`Carpet`). An attachment instead supplies T5's prepared `matchId` and `fingerprint`, with exactly the same operation/item/program. T8 owns presenting and retaining these identities in the wizard. Never call the ordinary dashboard match insert/fill path for a console submission.

The server rechecks the authenticated administrator, validates the actual file with `SwingVisionUploadStrategy` and `validateSwingVisionFile`, then parses it with the existing `SwingVisionParser`. No browser score, player name, storage path, actor or parser result is accepted. Canonical roster names must match the parsed player; attachment names, sets, tiebreaks, and winner must match the recorded result. Coach `Final Score` and the parser's winner label are compatible for equal completed scores; absent tiebreak arrays are equivalent to all-null arrays. The original result string and score object are preserved. Retired/defaulted recorded endings are refused because the export parser does not establish that ending. Refusals direct the user to the matching file rather than changing a recorded result.

Storage is immutable and content-addressed under `_admin-console/operation/item/sha256.xlsx`; a restrictive storage policy excludes all browser access to that namespace. A lost storage response is recovered only after reading and verifying identical bytes. Rejected database submissions may leave an unlinked object in this namespace; no match, file row or audit is left by a refused transaction. Garbage collection of those unlinked blobs is not implemented here.

`admin_submit_match_file` is service-role-only. Its actor comes from the server session and is rechecked in SQL. In one transaction it locks the provenance operation/item, locks and revalidates the T5 reservation and full recorded snapshot when attaching, checks eligibility, links one match/file, creates one durable attempt, and records one audit. Retry with altered bytes/metadata is refused; identical retry returns the same row. A claimed roster user alias is not accepted in place of a canonical existing profile. The existing membership fallback remains available only when no unmerged profile owns that user.

`GET /api/admin/uploads/file?operationId=...&itemId=...` returns the durable match/file linkage and `queued`, `processing`, `completed`, or `failed`. Status reads require the submitting actor to still be an administrator. Submission awaits Edge dispatch, then reads this same state. A queued submission can retry with the same file. Once claimed, processing cannot be automatically replayed: the existing points/shots pipeline performs separate writes, so retry after a partial failure could duplicate analysis. Failed attempts explicitly require review. A worker interruption may leave `processing`; the status text also calls for review if that state persists. There is no automatic lease expiry or automatic recovery of partial writes: review is the administrator reconciliation control on the item in `/admin/uploads`. **Abandon** ("Abandon and delete match" for a console-created match, "Abandon" for an analysis attachment) shows for a `queued`, `processing` or `failed` attempt; **Mark complete** shows for `processing` alone. Both post to `reconcileAdminSubmissionAction` → `reconcileAdminSubmission` (`src/lib/services/programs/admin-reconciliation.ts`), which re-checks `requireAdmin` and calls the service-only `admin_reconcile_submission_item(p_actor_id, p_operation_id, p_item_id, p_mode)` with the session actor. Abandon deletes the attempt and the `match_files` row, rewrites the item to `failed`/`abandoned` ("Abandoned by an administrator"), reverts the match to manual and audits `console.submission_reconciled`; it is refused with `analysis-present` once `points` or `match_stats` exist. The RPC returns the deleted row's `storage_path` (also kept under the item's `result->'abandoned'`), and the service removes that `.xlsx` from `match-data` after the RPC commits, best-effort: the `_admin-console/` namespace is closed to browsers, so only the service-role client can reach it, and a refusal or error is logged under `[console abandon]` without failing the reconcile — nothing references the object once the transaction has committed. This applies to a console-created match and an analysis attachment alike. For a console-created match the service then purges storage and deletes the match (a purge failure stops before the delete). Mark complete sets the attempt `completed` when process-match wrote points and statistics but died before finishing, and is refused with `attempt-not-processing` or `analysis-missing`. A `completed` attempt refuses both (`attempt-completed`), and an item with no attempt is `attempt-missing`.

Every `process-match` request consults the durable match linkage, even if the request omits operation IDs. A console claim requires verified service dispatch or the original authenticated admin. The processor reads file/bucket/provider/actor only from the durable request, hashes the exact bytes it parses, and permits one claim. Legacy requests cannot use reserved console paths or encoded aliases. Stats formulas, point/shot generation, key moments and insights remain in the existing pipeline; live read-only inspection confirmed `calculate_match_stats(uuid)` writes `match_stats`, not recorded match fields.

While a file attempt is queued/processing, a database trigger protects participant identity, recorded score/result and event context, format, date, source/provider, and court fields. After completion/failure the existing authorized match editing and account/roster repair paths are available again. Competing files/jobs for a match with a console file attempt are refused under a parent-match lock; no second analysis is silently created.

## Deployment and verification

Migration `20260919044716_submit_admin_match_files.sql` depends on T2/T5 and was **applied live on 2026-09-19**; the repo file carries its live-recorded version (written as `20260917010000`). Live read-only catalog verification during T6 confirmed head `20260916183239`, the current matches/match_files/program_players columns, and the live `calculate_match_stats`, regraft and upload-transition definitions. No live data was mutated.

Deploy the migration before the updated `process-match` Edge function, and deploy both before exposing the console file endpoint. The Edge boundary now consults the new claim RPC on every request; deploying it without that migration will reject ordinary imports too. Deploying only the route with an old Edge function would omit the claim/hash safeguards and is not supported. No deployment was performed in T6.

Tests execute actual PostgreSQL migration code via PGlite, actual XLSX validation/parsing via ExcelJS, and the actual Edge entry boundary in a VM. They cover authorization, immutable content retries, one match/file/audit, mismatch rollback, reservation staleness, once-only claims, partial-failure states, active processing protection and post-processing repair, namespace policy/alias bypasses, and mutated processing bytes. Production async dispatch and deployed RLS remain rollout verification work.
