# Admin upload history (T15)

`getAdminUploadHistory` in `src/lib/data/admin-uploads-server.ts` returns one row per durable console operation, plus all its item outcomes. It is a server loader, not a server action. T16 owns the UI; no route is wired here.

Every call checks `requireAdmin` before creating either data client. Only `admin_upload_submissions.origin = admin_console` defines inclusion, independent of membership and match creator. Existing-result attachments and member-admin submissions therefore remain visible; ordinary dashboard writes do not acquire provenance. Session reads load provenance/items/file attempts under the new tables' admin SELECT RLS: those migrations intentionally grant no service-role access. After the guard, service reads hydrate existing programs, actors, events, matches, outcomes, exact linked jobs and published statistics, which nonmember admins cannot necessarily read through ordinary RLS.

The Date column is submission time. Team/actor/event/match labels are current persisted metadata, with explicit unavailable fallbacks. Item save status is distinct from subsequent processing. Counts expose saved, failed, pending and unrecognized save states; a mixed saved/unsaved operation is partial. Each item's state and failure remain available even when a row's aggregate cannot name one uniform state. Missing evidence or unrecognized states are unknown, never assumed complete. Outcomes preserve the actual saved kind, side and round. File state comes from its exact durable attempt. Video state comes from its exact linked job through `resolveAnalysisStatus` and `withStatsPublished`: vendor completion without a derivation version remains `processed` (Stats pending), derivation without published statistics is `timeline`, and published derived statistics permit `completed`. The item `result.state` snapshot is not authoritative for these projections.

Result IDs are metadata, not permission. A separate batched session `matches` SELECT supplies `matchHref` only for session-readable matches; nonmember administrators inspecting somebody else's recorded result receive no inaccessible dashboard link. No admin result-detail route is invented. Event/outcome IDs have no result href until an actual authorized destination exists.

Pagination orders descending by `created_at`, then `operation_id`, with a one-row lookahead and a strict versioned timestamp/UUID cursor. PostgreSQL microseconds survive encoding. Validated scalar syntax alone enters the PostgREST keyset expression. Page size is 1–100 (default 25). Related reads use deduplicated chunks of 100 IDs and range pages of 500, avoiding per-item calls and the default row-cap truncation. Any failed read returns an explicit error rather than empty history or guessed states.

No migration is added. Existing T2/T6/T7/T10/T11 migrations are deployment prerequisites; they were applied live on 2026-09-19 and the repo files carry their live-recorded versions. Root's SELECT-only catalog capture at 2026-09-17 03:54:52.627241 UTC confirmed existing base metadata columns and live migration head `20260916183239`; new provenance contracts are the source migrations. Tests run the actual loader with dependency fixtures covering authorization ordering, grant separation, malformed cursors, equal timestamps/microseconds, kinds/provenance, partial saves, real processing evidence, RLS-filtered links and paged batch reads. No live mutation, deployment or vendor processing was performed.
