# Admin dual results (T10)

The server-only `submitAdminDualResults` service accepts `AdminDualSubmissionInput` from `src/lib/admin/results/types.ts`. It resolves the authenticated administrator, validates the whole envelope, resolves the target program context, and calls service-role-only RPCs with the verified actor. It has no client-callable injectable action. T13 can wrap this boundary in a guarded action.

For an existing dual, load `getAdminDualResultContext(programId, eventId)` first and send its fingerprint. For a new dual, provide the complete nine-court lineup using program roster IDs. Each submission carries a stable operation UUID and each selected court a stable item UUID. Retries send exactly the same request and IDs. To change input, start a new operation; existing successes cannot be overwritten by a later operation.

Setup validates all supplied lines before writing, locks existing event/entries, and snapshots event and participant identity. A transaction creates or links the event once and registers all item intentions. Each result then runs in its own transaction, recording either a linked match/outcome plus one audit, or a durable failure. The boundary skips prior successes. If a response is lost, it reads durable state and returns pending items for a same-request retry. A failure to read state returns an explicit retry message.

Scores use the member schedule conventions: our side is player1, games and tiebreak points remain separate, nullable ad scoring stays nullable, doubles retain their pair labels and have no single player1 ID, and a stopped match awards the winner to the opposite side. A No player line requires its matching forfeit outcome and creates no match. Shared lineup validators run before RPC; SQL independently verifies roster identity and result shapes. There is no new rule requiring a score to look like a completed match.

The operation row serializes retries; entry version locks (`UPDATE id=id`) use the same mechanism as the live schedule guard. The additive result trigger blocks ordinary inserts into a pending or succeeded console target. It preserves ordinary corrections to an existing match. Failed intentions allow ordinary writes to proceed, and a later console retry observes their result and fails without overwriting it. Competing console operations lock the same entry; the loser records a conflict. Event/entry/legacy-forfeit changes stale-refuse on apply. No existing schedule function, policy or grant is replaced.

The verified live outcome guard requires member staff authorization whenever `auth.uid()` exists, including service-role calls. The service-only outcome RPC therefore clears the temporary subject claims solely around that INSERT, passes `actor_user_id` explicitly, and restores claims before provenance/audit and on caught failures. The reservation gate separately requires service role plus the private operation/item target; forged authenticated session tokens cannot use it. The migration exposes no authenticated mutation grant for this path.

Added 2026-09-27 (T24, `tests/database/admin-abandon-results.test.mjs`, migration `20260927094436_abandon_admin_result_items.sql`): a prepared dual whose browser never finished applying leaves its untouched lines reserved indefinitely — the reservation has no expiry and a retry needs the exact request that was lost. `admin_abandon_result_items(p_actor_id, p_operation_id)` is the service-role-only, SECURITY DEFINER way back for any **current** administrator, not only the operation's actor: it locks the submission, takes each still-pending item's entry version lock (`UPDATE id=id`) and marks it `failed`/`abandoned`, then writes one `console.submission_reconciled` audit row listing the abandoned item ids (a call that finds nothing pending changes nothing and audits nothing). Succeeded items, items failed for any other reason and every `admin_schedule_result_targets` row are untouched — the targets are history — and because the reservation trigger only honours `pending` or `succeeded` items, the coach can record those lines again at once. `abandoned` is the one terminal failure code: `admin_apply_dual_result` returns the saved status for an abandoned item exactly as it does for a succeeded one, so a same-request resume can never re-apply it or re-reserve the line, while every other failure code stays retryable.
